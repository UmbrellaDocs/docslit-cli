# Writing DocsLit docs

DocsLit builds a static docs site from Markdown files in `docs/` plus a `docslit.json` config. Pages can embed built-in `<wc-*>` web components directly in Markdown. No imports, no MDX.

This file is generated from the component manifest (`docslit components --json`). If it disagrees with the CLI, the CLI wins.

## Workflow

Never guess a component, attribute or config key. Ask the CLI. All of these print machine-readable output and never prompt.

1. `docslit components --json` lists every component. `docslit components wc-tabs --json` returns one component's attributes, nesting rules and example.
2. `docslit schema` prints the `docslit.json` JSON Schema. `docslit schema frontmatter` prints the page frontmatter schema.
3. `docslit new guides/setup --title "Set up" --group "Guides" --description "..." --json` creates the page and registers it in the sidebar. Use it instead of hand-editing the sidebar. (Skip `--group` when the sidebar is autogenerated.)
4. Write the page content.
5. `docslit validate --format json` checks that nothing is broken: links, assets, unknown components, frontmatter, sidebar. Exit code 1 means errors.
6. `docslit lint --format json` checks quality: descriptions, headings, code languages, alt text, link text, page length. Each issue has `file`, `line`, `code`, and a `fix` hint.
7. Fix every error, then the warnings, and re-run both until they are clean. Both accept a directory argument and `--strict` (warnings fail).

`docslit mcp` starts an MCP server (stdio) that exposes the same capabilities as tools. `docslit agents init` wires it into your editor config.

Preview with `docslit dev`; build with `docslit build` (output in `dist/`).

## Project layout

```text
docslit.json        site config and sidebar
docs/               pages (*.md); sub-folders are fine
docs/_reusables/    snippets pulled in with <wc-include src="..." />
components/         optional custom components (components/wc-name.js)
```

Page IDs map to files: `"quickstart"` is `docs/quickstart.md`, `"guides/setup"` is `docs/guides/setup.md`.

### docslit.json

```json
{
  "name": "My Docs",
  "description": "One sentence for SEO and llms.txt",
  "url": "https://docs.example.com",
  "sidebar": [
    { "group": "Getting started", "pages": ["introduction", "quickstart"] },
    { "group": "Guides", "autogenerate": "guides" }
  ]
}
```

Sidebar forms:

- Explicit: groups with a `pages` array of page IDs. Pages appear in the listed order, and every page should be listed or it is reported as an orphan.
- Per group: `"autogenerate": "folder"` (or `{ "directory": "folder", "collapsed": true }`) builds the group from a docs sub-folder.
- Whole site: `"sidebar": "auto"` derives everything from the folder tree. In auto mode order pages with frontmatter `sidebar_position` and hide one with `sidebar: false`. Do not edit the sidebar by hand to add pages; just create the file.

Other keys exist (`versions`, `i18n`, `openapi`, `theme`, `redirects`, `attributes`, `navbar`, `footer`, ...). Read `docslit schema` before adding any.

### Page frontmatter

```yaml
---
title: Set up the CLI
description: Install the CLI and run your first build in under five minutes.
sidebar_title: Set up
tag: Guide
---
```

- `title` is required. `description` should be a real sentence of 30 to 200 characters: it feeds search, SEO and `llms.txt`.
- Optional: `sidebar_title`, `tag`, `readtime` (string, e.g. `"3 min read"`), `updated`, `icon`, `draft: true`, `redirect`, `attributes` (page variables), `sidebar_position`, `sidebar`.
- Unknown keys are reported by `validate`. Check `docslit schema frontmatter`.

## Writing good pages

Pages are read by people and retrieved in chunks by LLMs. Write for both.

- One `# H1` that matches `title`, then `##` and `###` in order. Never skip a level. Do not repeat a heading text on one page (anchors collide).
- Lead with what the page is for, then the shortest working example, then detail. Prefer short sections that stand alone, since a retrieved chunk loses its neighbours.
- Every fenced code block has a language (` ```bash `, ` ```json `, ` ```text `).
- Every image has alt text that says what it shows.
- Link text describes the target ("see [the sidebar options](config)"), never "click here" or a bare URL.
- Keep pages under roughly 2500 words; split long ones. Keep paragraphs short.
- Use a component only when it beats plain Markdown: steps for ordered procedures, tabs or code groups for per-language variants, callouts sparingly (a handful per page at most), GFM tables for ordinary tables.
- Never leave `TODO`, `FIXME`, `TBD` or placeholder text in prose.
- Internal links use page slugs relative to the current page, e.g. `[Setup](setup)` or `[Setup](../guides/setup)`, without `.md`.
- Variables: define `{{NAME}}` in `docslit.json` `attributes`, page frontmatter `attributes`, or `<wc-var name="NAME" value="..." />`. Use UPPER_SNAKE_CASE. An undefined placeholder is a validate warning.

## Component rules

1. Put a blank line before and after every block-level `<wc-*>` element, and a blank line after the opening tag of any element whose body is Markdown (callouts, steps, tabs, panels, ...). Without it the body is not rendered as Markdown.
2. Do not indent component tags or their bodies by 4+ spaces: Markdown turns them into code blocks.
3. Always write explicit closing tags: `<wc-tile ...></wc-tile>`, never `<wc-tile ... />` (these are HTML custom elements, not JSX). Only the compile-time tags `wc-include` and `wc-var` (declaration form) are written self-closing: `<wc-include src="snippet.md" />`.
4. Respect nesting: containers hold only their listed children (see each component's "Children" and "Parent"). Inside `wc-tabs`, use `wc-tab`; inside `wc-steps`, `wc-step`; inside `wc-code-group`, `wc-code-tab`; and so on.
5. "raw" bodies (`wc-code-block`, `wc-code-tab`, `wc-mermaid`, `wc-asciidoc-table`) are not Markdown; write the text exactly as it should appear.
6. Use `icon-name` (not `icon`) for named icons on `wc-card` and `wc-tile`. Tabs use `label`, not `title`.
7. Pass JSON attributes with single quotes around the value: `rows='[["a","b"]]'`.
8. Do not invent tags or attributes. An unknown `wc-*` tag is a validate warning and renders as an unstyled element.
9. The `theme="dark|light"` attribute pins any themable component to a color scheme. It is omitted from the per-component lists below.
10. Migrating MDX or Mintlify content? Use `docslit import <dir>` or follow the docslit-migrate skill.

## Icons

`wc-icon name`, `icon-name` on cards and tiles, and page `icon` accept built-in Lucide-style names (for example `check`, `x`, `warning`, `info`, `arrow-right`, `external-link`, `code`, `terminal`, `file`, `folder`, `search`, `star`, `zap`, `book`, `settings`, `user`, `home`, `lock`, `package`, `globe`, `cpu`). Other names fall back to Font Awesome class names, fetched at runtime.
